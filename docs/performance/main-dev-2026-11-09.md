## Branch changes

- Main: `73375a2` reverts only the Three.js prototype commit `22ecd20`. Compared with pre-prototype `5132395`, the only difference is the retained .gitignore. Earlier Canvas optimizations and the draggable lighting development panel remain intact.

- Both branches have identical .gitignore content: node_modules/, dist/, .local/. Git blob: `12c3f65ce938faa9b1002be8f66d02d6f7843bbd`. Dev already contained these rules, so no duplicate change was needed.

## Method

Chromium 149.0.7827.55; ANGLE (AMD, AMD Radeon 780M Graphics (0x000015BF) Direct3D11 vs_5_0 ps_5_0, D3D11); Node 24.18.0. Main was served as its original static scripts. Dev was built in production mode with Vite 8.3.6, with no development server or HMR. An API hook was added to test copies only; normal simulation/rendering functions were timed without wrappers. Audio and network transport were excluded from both sides.

Fixed seed 1234567, all six races, normal AI, 90 seconds of deterministic preparation. Desktop viewport 1440 x 900 at DPR 1; portrait viewport 390 x 844 at DPR 2 with the sidebar closed. Canvas effect density, camera and state were equal. Start and end snapshot hashes match between branches and repetitions. No browser errors occurred.

- Pure render: 0, 4 and 12 level-four explosions (0, 801 and 1,964 particles). FX state is frozen; the existing second-flash timer is allowed to settle before timing. Four alternating branch-order rounds, 60 warmup and 120 measured RAF frames per scene.
- Full loop: seven incoming missiles with flight extended equally to 120 seconds. Fixed 1/60-second advancement drives simulation, FX, fire input, UI and draw in their original order. Native RAF paces rendering. Initial exploratory runs used 60 warmup / 240 measured frames, three rounds per branch/viewport.
- Confirmation: because short-run order/noise affected the initial results, use 180 warmup / 600 measured frames, two rounds in opposite branch order per viewport. Full-loop results below refer to this longer window.
- Table values are the median of round-average synchronous CPU milliseconds per frame; P95 is the median of round P95s. They measure CPU submission, not GPU completion or power. CDP TaskDuration and LayoutDuration are additional main-thread measurements. Heap values in raw reports are not a retained-memory/leak measurement.

## CPU results

Lower is better. Positive change means dev took longer.

| Scenario | main ms/frame | dev ms/frame | dev change | P95 main / dev ms |
| --- | ---: | ---: | ---: | ---: |
| Canvas idle | 0.61 | 0.56 | -8.0% | 1.00 / 0.95 |
| Canvas 801 particles | 1.60 | 1.55 | -3.3% | 2.25 / 2.15 |
| Canvas 1,964 particles | 2.45 | 2.65 | +8.2% | 3.50 / 3.55 |
| Full loop desktop | 1.10 | 1.08 | -2.5% | 1.95 / 1.75 |
| Full loop portrait | 0.81 | 0.91 | +12.4% | 1.35 / 1.55 |

Round-average ranges:

- Canvas idle: main 0.56–0.70 ms; dev 0.51–0.85 ms.
- Canvas 801 particles: main 1.35–1.83 ms; dev 1.31–1.77 ms.
- Canvas 1,964 particles: main 2.29–2.75 ms; dev 2.42–2.87 ms.
- Full loop desktop: main 1.10–1.11 ms; dev 0.94–1.21 ms.
- Full loop portrait: main 0.74–0.88 ms; dev 0.90–0.93 ms.

Most ranges overlap and the desktop full-loop ordering changes between rounds. In the portrait confirmation cases, dev took longer in both rounds. This does not establish a consistent overall speedup from the refactor. The short exploratory sample showed larger apparent regressions; the longer confirmation window is the basis of the headline comparison. Both branches retained approximately 16.67 ms RAF intervals in these cases; no material FPS difference was demonstrated.

## Optional Pixi comparison

Dev's particle switch was also tested separately with 1,964 particles: 2.93 ms/frame, P95 4.40 ms; round-average range 2.73–3.27 ms across three runs. Main Canvas is 2.45 ms and dev Canvas is 2.65 ms. This sample does not establish a consistent advantage sufficient to enable GPU batches by default. This separate sample is not included in the default branch comparison. It repeats the same 0/4/12-explosion preparation order as the Canvas tests. An initial three-run GPU diagnostic used different preparation history and had a different start-state hash; it is excluded from comparisons and marked as such in the raw data.
